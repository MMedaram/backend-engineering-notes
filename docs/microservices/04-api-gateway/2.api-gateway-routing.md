# API Gateway Routing with Eureka

> Routing chooses a service. Discovery provides its instance addresses.
> Load balancing chooses an instance. The gateway forwards the request.

These notes cover automatic discovery routes, explicit routes, single-host and
multiple-host deployments, and default/custom load-balancing algorithms.

---

## 1. The four responsibilities

| Responsibility   | Question answered                                 | Component                           |
|------------------|---------------------------------------------------|-------------------------------------|
| Routing          | Which service should handle this API?             | Gateway route definition            |
| Discovery        | Where are the service instances?                  | Eureka client/discovery information |
| Load balancing   | Which instance receives this request?             | Gateway's load-balancing component  |
| Reverse proxying | Who forwards the request and relays the response? | Gateway                             |

Eureka stores registrations; it normally does not forward business requests.
Clients cache registrations, so a business request does not require a fresh
Eureka query every time.

The gateway needs a destination, not separate routing rules for every server.

---

## 2. Example applications and controller paths

Assume these applications exist:

- Eureka Server
- API Gateway
- Config Service
- Branch Service
- Customer Service
- Account Service
- Notification Service

For the examples, backend controllers accept:

| Service                | Example backend path |
|------------------------|----------------------|
| `branch-service`       | `/branches/10`       |
| `customer-service`     | `/customers/42`      |
| `account-service`      | `/accounts/100`      |
| `notification-service` | `/notifications/500` |

The Config Service supplies application configuration. Registering it in Eureka
does not mean it should have a publicly accessible gateway route. The gateway
itself also does not need a public route pointing back to itself.

---

## 3. Case 1: one server, one instance per service

Server A: `10.10.1.10`.

| Application          | Address           |
|----------------------|-------------------|
| Eureka Server        | `10.10.1.10:8761` |
| API Gateway          | `10.10.1.10:8080` |
| Config Service       | `10.10.1.10:8888` |
| Branch Service       | `10.10.1.10:8101` |
| Customer Service     | `10.10.1.10:8102` |
| Account Service      | `10.10.1.10:8103` |
| Notification Service | `10.10.1.10:8104` |

Assume separate Spring Boot processes using the same host network. Their
listening ports must differ to avoid binding conflicts. Container network
isolation can change port arrangements, but the advertised host/port must still
be reachable by the gateway.

With one instance per business service, discovery supplies one candidate for
each service. There is no choice among multiple instances yet.

---

## 4. Case 2: additional instances on another server

Server B: `10.10.1.20`.

| Service                | Server A          | Server B          |
|------------------------|-------------------|-------------------|
| `branch-service`       | `10.10.1.10:8101` | —                 |
| `customer-service`     | `10.10.1.10:8102` | `10.10.1.20:8102` |
| `account-service`      | `10.10.1.10:8103` | `10.10.1.20:8103` |
| `notification-service` | `10.10.1.10:8104` | —                 |

The same port can be used on different servers. Eureka groups the two Customer
instances under the same service name, with separate instance identities.

```text
CUSTOMER-SERVICE
    10.10.1.10:8102
    10.10.1.20:8102

ACCOUNT-SERVICE
    10.10.1.10:8103
    10.10.1.20:8103
```

Do not name these `customer-service-1` and `customer-service-2` if they are meant
to be interchangeable instances of one logical service.

## 5. Correct Eureka registration

Example Customer Service `application.yml`:

```yaml
spring:
  application:
    name: customer-service

server:
  port: 8102

eureka:
  client:
    service-url:
      defaultZone: http://10.10.1.10:8761/eureka/

  instance:
    prefer-ip-address: true
    ip-address: ${SERVICE_IP}
    instance-id: "${spring.application.name}:${eureka.instance.ip-address}:${server.port}"
```

Supply the environment variable for each deployment:

| Instance             | `SERVICE_IP` | Resulting instance ID              |
|----------------------|--------------|------------------------------------|
| Customer on Server A | `10.10.1.10` | `customer-service:10.10.1.10:8102` |
| Customer on Server B | `10.10.1.20` | `customer-service:10.10.1.20:8102` |

This is one explicit IP-based approach. Resolvable hostnames are also valid.

### Registration rules to remember

1. Same logical service: same `spring.application.name`.
2. Each instance: unique instance ID within that service.
3. Advertised address/port: reachable from the gateway.
4. `defaultZone`: retain this exact camel-case map key.
5. Gateway/service firewall rules: allow the required traffic.
6. Application listener: bind to an interface the gateway can reach.

Do not advertise `localhost` for a service that another server must call.
`localhost` always refers to the machine making the connection.

## 6. Dependencies and configuration version

The gateway needs:

- A compatible Spring Cloud Gateway starter
- `spring-cloud-starter-netflix-eureka-client`
- `spring-cloud-starter-loadbalancer`

Business applications need the Eureka client to register. They do not need the
Gateway starter just because traffic arrives through a gateway.

Use compatible Spring Boot/Spring Cloud versions and the appropriate Spring
Cloud BOM. Do not independently select arbitrary dependency versions.

The following examples use the namespaced **Gateway Server WebFlux** properties:

```text
spring.cloud.gateway.server.webflux.routes
spring.cloud.gateway.server.webflux.discovery.locator
```

Older Gateway versions commonly use:

```text
spring.cloud.gateway.routes
spring.cloud.gateway.discovery.locator
```

Check the version in your project before copying configuration. These examples
are for the WebFlux gateway; Web MVC configuration can differ.

## 7. Method 1: automatic discovery routes

The Discovery Locator generates routes from discovered service names. By
default, it creates a service-name path and an `lb://` destination, and strips
the service-name prefix before forwarding.

### Gateway `application.yml`

```yaml
server:
  port: 8080

spring:
  application:
    name: api-gateway

  cloud:
    gateway:
      server:
        webflux:
          discovery:
            locator:
              enabled: true
              lower-case-service-id: true
              include-expression: >-
                serviceId.toLowerCase() == 'branch-service'
                or serviceId.toLowerCase() == 'customer-service'
                or serviceId.toLowerCase() == 'account-service'
                or serviceId.toLowerCase() == 'notification-service'

eureka:
  client:
    service-url:
      defaultZone: http://10.10.1.10:8761/eureka/
    fetch-registry: true
```

The inclusion expression selects the four business services. It avoids
automatically exposing Config Service or generating a self-route for the
gateway. It does not replace authentication or authorization.

### Public-to-backend mapping

| Client request path                       | Backend receives     |
|-------------------------------------------|----------------------|
| `/branch-service/branches/10`             | `/branches/10`       |
| `/customer-service/customers/42`          | `/customers/42`      |
| `/account-service/accounts/100`           | `/accounts/100`      |
| `/notification-service/notifications/500` | `/notifications/500` |

Example request:

```http
GET http://10.10.1.10:8080/customer-service/customers/42
```

### Processing steps

1. Gateway matches the generated `/customer-service/**` route.
2. The destination identifies `customer-service`.
3. Discovery provides eligible registered instances.
4. Load balancing selects an instance.
5. The generated rewrite removes `/customer-service`.
6. Gateway forwards `/customers/42` and relays the response.

In Case 1, the destination is `10.10.1.10:8102`. In Case 2, either Customer
instance can be selected. Adding another instance does not require another
public route.

If you customize discovery-route filters, preserve the path-rewrite behavior
you need. Replacing the default filter list without an equivalent rewrite can
send an unexpected service-name prefix to the backend and cause `404` errors.

## 8. Method 2: explicit routes with Eureka

Here, you choose the public URL and route it to a logical service name. Eureka
still supplies instance addresses because the URI uses `lb://`.

### Alternative gateway `application.yml`

```yaml
server:
  port: 8080

spring:
  application:
    name: api-gateway

  cloud:
    gateway:
      server:
        webflux:
          discovery:
            locator:
              enabled: false

          routes:
            - id: branch-route
              uri: lb://branch-service
              predicates:
                - Path=/api/branches/**
              filters:
                - StripPrefix=1

            - id: customer-route
              uri: lb://customer-service
              predicates:
                - Path=/api/customers/**
              filters:
                - StripPrefix=1

            - id: account-route
              uri: lb://account-service
              predicates:
                - Path=/api/accounts/**
              filters:
                - StripPrefix=1

            - id: notification-route
              uri: lb://notification-service
              predicates:
                - Path=/api/notifications/**
              filters:
                - StripPrefix=1

eureka:
  client:
    service-url:
      defaultZone: http://10.10.1.10:8761/eureka/
    fetch-registry: true
```

Use this configuration instead of the Method 1 example; do not paste both as
duplicate YAML root sections.

### Does `locator.enabled: false` disable Eureka?

No. It disables automatic route generation. The explicit `lb://` destinations
still use discovery and load balancing.

### Explain one route

| Setting                      | Meaning                                         |
|------------------------------|-------------------------------------------------|
| `id: customer-route`         | Identifies this route                           |
| `Path=/api/customers/**`     | Matches incoming Customer API requests          |
| `uri: lb://customer-service` | Resolve Customer Service and select an instance |
| `StripPrefix=1`              | Remove the first path segment, `api`            |

Example:

```text
Incoming: /api/customers/42
Backend:  /customers/42
```

The backend controller must accept the resulting path. Prefix removal is not
always necessary; it depends on the controller mappings and external contract.

### What changes between deployment cases?

| Case            | Customer destinations                             | Gateway route changes? |
|-----------------|---------------------------------------------------|------------------------|
| One instance    | `10.10.1.10:8102`                                 | No                     |
| Two instances   | `10.10.1.10:8102`, `10.10.1.20:8102`              | No                     |
| Three instances | The two above plus a third reachable registration | No                     |

The discovered candidate list changes, while the public route remains stable.

## 9. Explicit route with a fixed address

Compare the discovery destination:

```yaml
uri: lb://customer-service
```

with a fixed destination:

```yaml
uri: http://10.10.1.10:8102
```

The fixed destination does not automatically use another Customer instance just
because Eureka knows it exists. If that URL points to a separate load balancer,
that component can distribute traffic, but that is a separate balancing layer.

### Method comparison

| Question                                  | Automatic discovery routes    | Explicit `lb://` routes          | Explicit fixed URL            |
|-------------------------------------------|-------------------------------|----------------------------------|-------------------------------|
| Who creates routes?                       | Discovery Locator             | Developer/configuration owner    | Developer/configuration owner |
| Public URL style                          | Usually includes service name | Chosen API contract              | Chosen API contract           |
| Where are backend addresses found?        | Discovery                     | Discovery                        | Configured destination        |
| New service instance needs another route? | No                            | No                               | Not automatically used        |
| Typical advantage                         | Convenient route generation   | Stable, controlled external APIs | Simple fixed destination      |

For a banking API, explicit routes with `lb://` are often a useful starting
point: expose selected APIs deliberately while retaining dynamic instance
discovery.

## 10. Default algorithm: Round Robin

With **Spring Cloud LoadBalancer**, the default instance-selection algorithm is
Round Robin unless overridden. This statement is about Spring Cloud
LoadBalancer; an older application using Netflix Ribbon may behave differently.

Assume three eligible instances:

```text
A = 10.10.1.10:8102
B = 10.10.1.20:8102
C = 10.10.1.30:8102
```

An illustrative sequence is:

```text
Request 1 → A
Request 2 → B
Request 3 → C
Request 4 → A
Request 5 → B
Request 6 → C
```

The initial position can differ. Discovery-list changes, retries, customized
instance suppliers, and multiple gateway instances affect the observed order.
Do not expect one exact global sequence across the whole deployment.

### Do we enable Round Robin explicitly?

Normally no additional algorithm configuration is needed when the required
discovery/load-balancer components and `lb://` route are present.

```xml
<dependency>
    <groupId>org.springframework.cloud</groupId>
    <artifactId>spring-cloud-starter-loadbalancer</artifactId>
</dependency>
```

Use the dependency version managed by the compatible Spring Cloud BOM.

Round Robin distributes turns. It does not measure whether each instance is
equally busy or whether requests have equal CPU/database cost.

## 11. Change the algorithm for one service

Example: use Random for `customer-service`, while other services retain their
default selection strategy.

### Gateway application

```java
import org.springframework.boot.SpringApplication;
import org.springframework.boot.autoconfigure.SpringBootApplication;
import org.springframework.cloud.loadbalancer.annotation.LoadBalancerClient;

@SpringBootApplication
@LoadBalancerClient(
    name = "customer-service",
    configuration = CustomerLoadBalancerConfiguration.class
)
public class ApiGatewayApplication {

    public static void main(String[] args) {
        SpringApplication.run(ApiGatewayApplication.class, args);
    }
}
```

### Service-specific load-balancer configuration

```java
import org.springframework.cloud.client.ServiceInstance;
import org.springframework.cloud.client.loadbalancer.reactive.ReactorLoadBalancer;
import org.springframework.cloud.loadbalancer.core.RandomLoadBalancer;
import org.springframework.cloud.loadbalancer.core.ServiceInstanceListSupplier;
import org.springframework.cloud.loadbalancer.support.LoadBalancerClientFactory;
import org.springframework.context.annotation.Bean;
import org.springframework.core.env.Environment;

public class CustomerLoadBalancerConfiguration {

    @Bean
    ReactorLoadBalancer<ServiceInstance> randomLoadBalancer(
            Environment environment,
            LoadBalancerClientFactory factory) {

        String serviceId = environment.getProperty(
                LoadBalancerClientFactory.PROPERTY_NAME);

        return new RandomLoadBalancer(
                factory.getLazyProvider(
                        serviceId,
                        ServiceInstanceListSupplier.class),
                serviceId);
    }
}
```

The second class intentionally has **no `@Configuration` annotation**. Do not
register service-specific configuration globally through component scanning;
it is supplied through `@LoadBalancerClient`.

Use the service identifier that the gateway resolves. Confirm the API and
dependencies against your actual Spring Cloud version before applying changes.

### Result

| Route destination       | Selection strategy                              |
|-------------------------|-------------------------------------------------|
| `lb://customer-service` | Random                                          |
| `lb://account-service`  | Default Round Robin, assuming no other override |

Random can choose the same instance repeatedly. It does not promise equal
counts over a small number of requests.

## 12. Where does algorithm configuration belong?

Configure the component making the instance-selection decision:

| Request path                                              | Selection configured in |
|-----------------------------------------------------------|-------------------------|
| Client → Gateway → Customer instance                      | Gateway                 |
| Account Service → Customer through a load-balanced client | Account Service         |
| Client → infrastructure balancer → Gateway instance       | Infrastructure balancer |

Customer Service normally does not select which Customer instance receives its
incoming requests.

There is no universal property such as:

```properties
# Not a standard Spring Cloud LoadBalancer property:
spring.cloud.loadbalancer.algorithm=least-connections
```

Properties configure supported features; selection strategies can use Java
extension points. Do not assume every NGINX, F5, or OCI algorithm is available
as a Spring property. Weighted or more specialized selection depends on the
framework version and implementation.

## 13. Discovery updates, failures, and practical limitations

- A new instance becomes eligible after registration/discovery information propagates.
- A failed instance can remain in cached information briefly; removal is not instantaneous.
- Heartbeats, application readiness, and request success are related but different signals.
- Multiple gateway instances usually maintain independent selection state.
- Adding instances does not increase a shared database's or provider's capacity.
- A timeout does not prove a state-changing request failed; use idempotency for safe retries.
- All services on one physical server share a host-level failure domain.

Gateway registration in Eureka and gateway discovery are separate capabilities.
The gateway needs to fetch registrations to resolve `lb://` destinations. Whether
it must register itself depends on how other components discover the gateway.

## 14. Troubleshooting checklist

| Symptom                             | Check                                                                                |
|-------------------------------------|--------------------------------------------------------------------------------------|
| Gateway `404`                       | Does any route match the public path/method?                                         |
| Backend `404`                       | Does the rewritten path match controller mappings?                                   |
| No instance available               | Service ID, registration state, discovery cache, dependencies                        |
| Connection refused or timeout       | Advertised IP/port, network listener, firewall, backend process                      |
| Only one instance receives requests | Fixed route URI, registrations, custom selection rules, affinity                     |
| One instance disappears from Eureka | Duplicate instance IDs or registration/heartbeat problems                            |
| Gateway connects to itself          | Incorrect `localhost` registration or an unintended self-route                       |
| Unequal request counts              | Observe more traffic; check multiple gateways, retries, filters, and candidate lists |

Useful verification steps:

1. Check Eureka shows each intended instance under the same service name.
2. Confirm the gateway can connect to every advertised address.
3. Inspect the effective route definition and destination scheme.
4. Confirm the backend receives the intended path.
5. Correlate gateway and backend logs using request IDs and instance identity.

For a learning environment, an instance-ID log entry or controlled diagnostic
endpoint can show which instance served a request. Avoid exposing internal
network details through public production responses unnecessarily.

## Practice questions and answers

### 1. Two Customer instances have different IPs. Must we add two gateway routes?

**Answer:** No. Use one `lb://customer-service` route. Eureka supplies both
instance addresses, and the load-balancer component selects one.

### 2. Does disabling Discovery Locator disable Eureka?

**Answer:** No. It disables automatic route generation. Explicit `lb://` routes
can still discover instances through Eureka.

### 3. Why is a route with `http://10.10.1.10:8102` not using the second instance?

**Answer:** The route has a fixed destination. Use a discovery-backed `lb://`
destination if the gateway should select among registered instances.

### 4. What happens to `/api/accounts/100` with `StripPrefix=1`?

**Answer:** The first segment, `api`, is removed. The backend receives
`/accounts/100`.

### 5. Where should Random selection be configured for gateway-to-Customer calls?

**Answer:** In the gateway's load-balancer configuration for that service ID.
Configuring a load-balanced client in another service affects that client's
outbound calls, not the gateway's selection.

### 6. Will requests alternate perfectly across two gateway instances?

**Answer:** No. Each gateway can have its own selection state. Instance-list
changes, retries, and traffic arrival patterns also affect the combined result.

### 7. Can both Customer instances register as `customer-service:8102`?

**Answer:** They need distinct instance IDs within the same service. Include a
unique host/IP and port, or another appropriate unique deployment identifier.

### 8. Why exclude Config Service and the gateway from automatically generated routes?

**Answer:** Registration is not permission to expose an application externally.
Expose only intended APIs, with appropriate security and routing policies.

## Quick revision

1. One logical service name can represent many instances.
2. Every registered instance needs a distinct identity and reachable address.
3. Automatic routes are generated; explicit routes are written by you.
4. Both can use Eureka through `lb://` destinations.
5. Fixed IP destinations do not automatically use Eureka alternatives.
6. Spring Cloud LoadBalancer defaults to Round Robin unless overridden.
7. Configure selection where the outbound backend choice is made.
8. Adding a service instance normally changes discovery data, not the public route.
