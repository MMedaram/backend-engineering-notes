# Java 15 Core Library, Runtime, and Tooling Improvements

## Overview

Java 15 added a small but useful collection of improvements around common APIs, framework-generated classes, and operational tooling. They are not a single language feature, but they matter for framework authors, backend services, and production diagnostics.

## `CharSequence.isEmpty()`

`CharSequence` gained `isEmpty()`, allowing generic code to ask whether a `String`, `StringBuilder`, `CharBuffer`, or another implementation has no characters without coupling to `String`.

```java
boolean isBlankInput(CharSequence value) {
    return value == null || value.isEmpty();
}
```

`isEmpty()` means length is zero; it does not treat whitespace as empty. Use `String.isBlank()` only when the value is known to be a `String` and whitespace-only input is invalid.

### Production guidance

- Prefer `CharSequence` in APIs that only need read-only character access.
- Do not call `toString()` merely to test emptiness; that may allocate for some implementations.
- Keep `null` policy explicit—`isEmpty()` is an instance method and does not handle `null`.

## Hidden Classes

Hidden classes (JEP 371) are class-file based classes intended for runtime frameworks that generate implementation details. They cannot be discovered by normal class loading and are designed to be unloaded independently of the defining class loader.

Frameworks such as dependency injection, proxies, expression engines, bytecode generators, and dynamic language runtimes benefit more directly than typical Spring Boot application code.

```java
MethodHandles.Lookup lookup = MethodHandles.lookup();
MethodHandles.Lookup hiddenLookup = lookup.defineHiddenClass(
    bytes,
    true,
    MethodHandles.Lookup.ClassOption.NESTMATE
);
Class<?> generated = hiddenLookup.lookupClass();
```

### Internal and JVM behavior

The JVM treats a hidden class as a non-discoverable implementation detail. Its name is not intended to be stable or used as a lookup key. The class can access nestmate members when the appropriate option is chosen, reducing synthetic accessor requirements for generated code.

### Best practices

- Application teams should normally consume hidden-class support through libraries, not generate hidden classes directly.
- Keep generated bytecode version-compatible with the deployed JVM.
- Do not persist, serialize, or expose a hidden class name as an API contract.
- Verify class unloading with realistic class-loader lifecycles; generated classes still retain anything they reference.

## Compressed heap dumps with `jcmd`

Java 15 supports gzip-compressed heap dumps through `jcmd`, reducing disk and transfer cost during incident response.

```bash
jcmd <pid> GC.heap_dump -gz=1 /var/log/app/heap.hprof.gz
```

### Production guidance

- Ensure the target filesystem has enough temporary and final capacity; a heap dump can still be large.
- Protect heap dumps as sensitive artifacts: they can contain credentials, personal data, tokens, and request payloads.
- Document who can trigger dumps, where they are stored, retention, encryption, and secure transfer procedures.
- Test analysis-tool support for compressed dumps before an incident.

## Daily backend example

```java
public record SearchTerm(CharSequence value) {
    public SearchTerm {
        if (value == null || value.isEmpty()) {
            throw new IllegalArgumentException("search term is required");
        }
    }
}
```

Use this sparingly: a `String` is still the better public API type when the application needs stable serialization, normalization, or ownership of the value.

## Common mistakes

1. Treating `CharSequence.isEmpty()` as whitespace validation.
2. Introducing direct hidden-class bytecode generation into ordinary business services.
3. Assuming a compressed heap dump is safe to store in a shared location.
4. Confusing heap-dump compression with reduced pause time or reduced heap usage.
