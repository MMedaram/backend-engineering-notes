# Introduction & Why Virtual Threads?

# Introduction

Virtual Threads are one of the biggest improvements introduced in Java in the last 20 years.

For many years, Java applications used **Platform Threads** to execute tasks.

Platform Threads worked well for small and medium applications.

However, modern applications are very different.

Today we build

* REST APIs
* Microservices
* Banking Systems
* E-Commerce Applications
* Chat Applications
* Streaming Platforms

These applications may serve **thousands or even millions of users simultaneously**.

The old threading model started becoming a limitation.

Java 21 introduces **Virtual Threads** to solve this scalability problem.

---

# Before Learning Virtual Threads

First, we need to understand one simple question.

## What is a Thread?

A **Thread** is the smallest unit of execution inside a program.

Think of it as a worker that performs a task.

Example

Suppose your application receives a request.

```text
Customer Login

↓

Validate User

↓

Read Database

↓

Generate Response

↓

Return Response
```

Someone has to execute these steps.

That "someone" is a **Thread**.

Without a thread,

no Java code can execute.

---

# Simple Real-life Example

Imagine a bank.

There are customers waiting.

There are bank employees.

Each employee serves one customer.

```text
Customer 1  ---> Employee 1

Customer 2  ---> Employee 2

Customer 3  ---> Employee 3
```

Here,

Employee = Thread

Customer = Request

The employee performs all work for one customer.

---

# What is a Process?

A **Process** is a running application.

Examples

```text
Chrome

IntelliJ IDEA

Spring Boot Application

MySQL Server
```

Each one is a process.

Inside a process,

there can be multiple threads.

Example

```text
Spring Boot Application (Process)

│
├── Thread 1
├── Thread 2
├── Thread 3
└── Thread 4
```

A process owns

* memory
* files
* resources

Threads share those resources.

---

# Process vs Thread

| Process                      | Thread                            |
|------------------------------|-----------------------------------|
| Complete running application | Small unit of execution           |
| Has its own memory           | Shares process memory             |
| Heavy                        | Lightweight compared to a process |
| Contains one or more threads | Executes application code         |

Simple way to remember

```text
Application

↓

Process

↓

Threads

↓

Execute Tasks
```

---

# Why Do We Need Multiple Threads?

Imagine an online banking application.

Only one thread exists.

```text
Customer A

↓

Transfer ₹5,000

↓

Database Update

↓

Response
```

Now another customer logs in.

```text
Customer B

↓

Wait...
```

Customer B cannot continue until Customer A finishes.

This creates long waiting times.

Now imagine multiple threads.

```text
Thread 1 ---> Customer A

Thread 2 ---> Customer B

Thread 3 ---> Customer C

Thread 4 ---> Customer D
```

Now everyone can be served simultaneously.

This is why multithreading is important.

---

# Platform Threads

Before Java 21,

Java used **Platform Threads**.

Every time you created

```
new Thread(...)
```

Java asked the Operating System to create a real operating system thread.

Simple flow

```text
Java Thread

↓

Operating System Thread

↓

CPU executes it
```

This model worked for many years.

---

# Why Did Platform Threads Become a Problem?

Suppose your banking application receives

```text
100 Requests
```

Java creates

```text
100 Threads
```

No problem.

Now imagine

```text
10,000 Requests
```

Java may need

```text
10,000 Platform Threads
```

This becomes expensive.

Why?

Because Platform Threads are created by the Operating System.

Operating System threads are heavy.

---

# Why Are Platform Threads Heavy?

Every Platform Thread needs

* memory
* operating system resources
* scheduling
* stack space

Creating thousands of them consumes significant resources.

Even worse,

most web application threads spend most of their life **waiting**.

Waiting for

* database
* REST API
* Kafka
* Redis
* File System

Example

```text
Thread

↓

Call Database

↓

Wait...

↓

Wait...

↓

Wait...

↓

Database Responds

↓

Continue
```

During this waiting period,

the thread still exists.

It occupies memory.

---

# Banking Example

Suppose an online banking system receives

```text
50,000 login requests
```

Each request

* validates user
* calls database
* waits for response

Most of the time,

the thread is simply waiting.

```text
Request

↓

Database

↓

Waiting...

↓

Waiting...

↓

Waiting...
```

Thousands of Platform Threads remain idle,

but they still consume system resources.

This limits scalability.

---

# The Traditional Thread-per-Request Model

Most Java web applications followed this model.

```text
Request 1 ---> Thread 1

Request 2 ---> Thread 2

Request 3 ---> Thread 3

Request 4 ---> Thread 4
```

This is called

> **Thread-per-Request**

It is simple and easy to understand.

But it does not scale well when the number of concurrent requests becomes very large.

---

# What Was the Solution Before Virtual Threads?

Developers tried different approaches.

Examples

* Thread Pools
* Async Programming
* CompletableFuture
* Reactive Programming
* Event Loops

These approaches improved scalability,

but they also made applications more complex.

Many developers found asynchronous code difficult to write and debug.

---

# Why Were Virtual Threads Introduced?

Java wanted to achieve two goals.

### Goal 1

Keep the simple

```text
One Request

↓

One Thread
```

programming model.

---

### Goal 2

Allow applications to handle

* thousands
* hundreds of thousands
* even millions

of concurrent tasks efficiently.

Virtual Threads solve this problem.

---

# What are Virtual Threads?

A **Virtual Thread** is a lightweight thread managed primarily by the Java Virtual Machine (JVM), rather than being tied one-to-one with an operating system thread.

This allows Java to create a very large number of threads with much lower overhead.

Do not worry about **how** this happens.

We will learn that in **Next chapter**.

---

# Simple Real-life Analogy

Imagine a restaurant.

### Old Model (Platform Threads)

One waiter serves one table.

```text
Waiter 1 ---> Table 1

Waiter 2 ---> Table 2

Waiter 3 ---> Table 3
```

If 5,000 customers arrive,

you would need thousands of waiters.

Impossible.

---

### New Model (Virtual Threads)

A small number of waiters efficiently manage many tables by serving customers only when they actually need attention.

Customers waiting for food do not require a dedicated waiter standing beside them.

This is similar to how Virtual Threads improve resource usage.

(We will understand the exact mechanism in Part 2.)

---

# Platform Thread vs Virtual Thread (High-Level)

| Platform Thread                          | Virtual Thread                       |
|------------------------------------------|--------------------------------------|
| Heavy                                    | Lightweight                          |
| Created using Operating System resources | Managed primarily by the JVM         |
| Limited in number                        | Can be created in very large numbers |
| Higher memory usage                      | Much lower memory overhead           |
| Good for moderate concurrency            | Excellent for massive concurrency    |

---

# Advantages of Virtual Threads

* Simple programming model
* Better scalability
* Lower memory usage per thread
* Millions of concurrent tasks become practical
* No need to rewrite everything using reactive programming
* Easier to write, read, and debug than many asynchronous approaches

---

# What Virtual Threads Do NOT Solve

Virtual Threads are **not** a solution for every performance problem.

They do **not**

* make algorithms faster
* improve CPU-intensive calculations
* replace good database design
* replace caching
* replace efficient SQL queries

They mainly improve applications that spend a lot of time **waiting** for external resources.

---

# Where Should We Use Virtual Threads?

Excellent for

* REST APIs
* Spring Boot Applications
* Database calls
* File I/O
* HTTP clients
* Messaging systems
* Microservices

---

# Where Should We Avoid Them?

Virtual Threads are **not** automatically better for

* heavy mathematical calculations
* image processing
* video processing
* machine learning algorithms
* CPU-intensive work

For those cases,

the number of CPU cores usually matters more than the number of threads.

---

# Best Practices (Introduction)

✅ Use Virtual Threads for I/O-bound applications.

✅ Continue writing simple synchronous code.

✅ Do not assume Virtual Threads improve every workload.

✅ Understand the problem before replacing existing code.

---

# Common Misconceptions

### 1. Virtual Threads are faster than Platform Threads.

Not always.

They improve **scalability**, not necessarily execution speed.

---

### 2. Virtual Threads replace multithreading.

Wrong.

Virtual Threads **are still threads**.

They simply use a different execution model.

---

### 3. Virtual Threads replace asynchronous programming everywhere.

Not completely.

Some applications still benefit from asynchronous designs.

---

### 4. Every application should immediately migrate.

Wrong.

Applications should adopt Virtual Threads only where they solve a real scalability problem.


---

# Quick Revision

* A Thread executes Java code.
* A Process contains one or more Threads.
* Before Java 21, Java primarily used Platform Threads.
* Platform Threads are backed by operating system threads.
* Platform Threads become expensive at very high concurrency.
* Modern applications spend much of their time waiting for I/O.
* Virtual Threads are lightweight and managed primarily by the JVM.
* Virtual Threads improve scalability, not raw CPU performance.
* Virtual Threads are ideal for I/O-bound applications like REST APIs and microservices.

---

# One-line Summary

Virtual Threads were introduced in Java 21 to keep Java's simple thread-per-request programming model while allowing applications to handle massive numbers of concurrent tasks efficiently with much lower resource usage.
