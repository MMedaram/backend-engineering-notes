# Internal Working of Virtual Threads

----

## Before We Start

From Part 1 we learned

```text
One Request
↓
One Thread
```

This programming model is very easy.

The problem was

```text
10,000 Requests
↓
10,000 Platform Threads
↓
Huge Memory Usage
```

Now the question becomes

> **How can Java create millions of Virtual Threads without creating millions of Operating System Threads?**

The answer lies in how Virtual Threads work internally.

---

# First Understand Platform Threads

Suppose we create

```
Thread thread = new Thread(task);
thread.start();
```

Internally

```text
Java Thread
↓
Operating System Thread
↓
CPU Executes
```

One Java Thread

always owns

One Operating System Thread.

Relationship

```text
Java Thread
1
↓
1
Operating System Thread
```

This is called

**One-to-One Mapping**

---

# Real Example

Suppose

```text
100 Threads
```

Java requests

```text
100 OS Threads
```

Operating System creates

```text
100 Native Threads
```

Everything is simple.

---

# What happens with 50,000 Threads?

```text
Java
↓
50,000 Threads
↓
Operating System
↓
50,000 Native Threads
```

Now the Operating System becomes overloaded.

Why?

Because every OS Thread needs

* stack memory
* scheduling
* context switching
* operating system resources

This is why Platform Threads don't scale.

---

# Virtual Thread Idea

Java asked one question.

Instead of

```text
1 Java Thread
↓
1 OS Thread
```

Can we do

```text
Many Java Threads
↓
Few OS Threads
```

Answer

Yes.

That is exactly what Virtual Threads do.

---

# Virtual Thread Architecture

Instead of

```text
Virtual Thread
↓
Own Operating System Thread
```

Java does

```text
Virtual Thread
↓
Carrier Thread
↓
Operating System Thread
```

Notice

Virtual Threads no longer own Operating System Threads.

They temporarily use them.

This is the biggest difference.

---

# What is a Carrier Thread?

A **Carrier Thread** is simply a normal Platform Thread.

Its job is to temporarily execute Virtual Threads.

Think of it as

A vehicle.

It carries Virtual Threads whenever they need CPU time.

---

# Banking Example

Imagine

100 bank customers.

Old model

```text
100 Customers
↓
100 Employees
```

Very expensive.

Virtual Thread model

```text
100 Customers
↓
10 Employees
↓

Serve one customer
↓
Move to next customer
↓
Move to next customer
```

Employees are

Carrier Threads.

Customers are

Virtual Threads.

---

# Relationship

```text
Virtual Thread
↓
Carrier Thread
↓
Operating System Thread
```

Many Virtual Threads

share

Few Carrier Threads.

---

# Example

Suppose

```text
100,000 Virtual Threads
```

Java may only use

```text
12 Carrier Threads
```

(if your machine has around 12 CPU cores).

Huge difference.

---

# What is Mounting?

Suppose

Virtual Thread wants to execute.

Java temporarily places it onto

a Carrier Thread.

This is called

**Mounting**

Simple picture

```text
Virtual Thread
↓
Mounted
↓
Carrier Thread
↓
CPU
```

Now the Virtual Thread starts running.

---

# What is Unmounting?

Suppose the Virtual Thread executes

```java
databaseCall();
```

Now it has to wait.

Instead of keeping the Carrier Thread idle,

Java removes the Virtual Thread.

This is called

**Unmounting**

Picture

```text
Virtual Thread
↓
Waiting
↓
Removed
↓
Carrier Thread becomes free
```

The Carrier Thread immediately starts working on another Virtual Thread.

---

# Why is this Amazing?

Imagine

Database takes

```text
2 Seconds
```

Old Platform Thread

```text
Thread
↓
Waiting...
↓
Waiting...
↓
Waiting...
↓
Still Occupied
```

Nothing useful happens.

The thread just waits.

---

Virtual Thread

```text
Database Call
↓
Waiting
↓
Unmount
↓
Carrier Thread Free
↓
Another Virtual Thread Executes
```

Huge improvement.

---

# What is Parking?

Parking means

The Virtual Thread is temporarily paused because it is waiting.

Example

```java
databaseCall();
```

or

```
httpClient.send();
```

or

```
Thread.sleep();
```

Instead of blocking an expensive OS Thread,

Java parks the Virtual Thread.

Think of Parking as

```text
Pause
↓
Wait
↓
Resume Later
```

---

# Example

Suppose

Customer wants account details.

```text
Virtual Thread
↓
Call Database
↓
Park
↓
Carrier Thread Free
↓
Another Customer Served
```

When database responds

```text
Resume
↓
Continue Execution
```

---

# What is Resuming?

When the waiting finishes,

Java simply mounts the Virtual Thread again.

```text
Virtual Thread
↓
Mounted Again
↓
Carrier Thread
↓
Continue Execution
```

Notice

It may resume on

a different Carrier Thread.

It doesn't matter.

---

# Scheduler

Who decides

which Virtual Thread gets CPU?

The

**Virtual Thread Scheduler**

Its job is

* choose Virtual Thread
* assign Carrier Thread
* mount
* unmount
* resume

You don't manage this.

The JVM does it automatically.

---

# Complete Flow

Suppose

Customer transfers money.

```text
Virtual Thread Starts
↓
Mounted
↓
Carrier Thread
↓
Validate Customer
↓
Call Database
↓
Park
↓
Carrier Thread Free
↓
Another Virtual Thread Runs
↓
Database Response
↓
Mount Again
↓
Continue
↓
Response Sent
↓
Finished
```

This is the life cycle of most Virtual Threads.

---

# What is Pinning?

Normally

Virtual Threads can unmount.

But sometimes

Java cannot remove them.

They become

**Pinned**

Meaning

The Carrier Thread cannot be released.

Example situations

* holding certain synchronized locks
* some native method calls
* specific blocking operations

When pinned

```text
Virtual Thread
↓
Carrier Thread
↓
Waiting
↓
Carrier Thread Cannot Be Reused
```

This reduces scalability.

We'll study pinning in detail in Part 4.

---

# Why Virtual Threads Scale Better

Platform Thread

```text
Waiting
↓
Still Uses OS Thread
```

Virtual Thread

```text
Waiting
↓
Carrier Thread Released
↓
Another Virtual Thread Runs
```

Carrier Threads stay busy doing useful work instead of waiting.

# Important Points

Virtual Threads

✔ are real Java Threads

✔ are **not** thread pools

✔ are **not** asynchronous callbacks

✔ still execute normal Java code

✔ simply use a different execution model

---

# Common Misconceptions

## 1. Carrier Thread belongs to one Virtual Thread

Wrong.

Many Virtual Threads use the same Carrier Thread over time.

---

## 2. Virtual Thread always runs on the same Carrier Thread

Wrong.

It may resume on a different Carrier Thread.

---

## 3. Parking means the thread is destroyed

Wrong.

It is only paused.

Later it resumes.

---

## 4. Mounting creates a new OS Thread

Wrong.

Java reuses existing Carrier Threads.

---

# Best Practices

✅ Write normal synchronous Java code.

✅ Let the JVM manage scheduling.

✅ Use Virtual Threads for I/O-bound work.

✅ Avoid unnecessary synchronization that may cause pinning.

---


# Quick Revision

* Platform Threads have a one-to-one relationship with OS threads.
* Virtual Threads are executed using Carrier Threads.
* A Carrier Thread is a normal Platform Thread.
* Mounting means assigning a Virtual Thread to a Carrier Thread.
* Unmounting releases the Carrier Thread while the Virtual Thread waits.
* Parking temporarily pauses a Virtual Thread.
* The JVM scheduler manages mounting, unmounting, and resuming.
* Pinning prevents a Virtual Thread from releasing its Carrier Thread.
* Virtual Threads scale because waiting tasks do not occupy Carrier Threads.

---

# One-line Summary

Virtual Threads achieve massive scalability by allowing the JVM to mount lightweight Virtual Threads onto a small number of Carrier Threads, releasing those Carrier Threads whenever a Virtual Thread waits for I/O, and reusing them to execute other work.
